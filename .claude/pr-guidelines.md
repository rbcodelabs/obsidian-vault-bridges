# PR Guidelines — Obsidian Vault Bridges

Generated by the pr-checklist skill. Edit freely.

## ⚠️ CI does not enforce this checklist

`.github/workflows/ci.yml` only runs `npm run build` (type-check + esbuild
bundle) on push/PR to `main`. **It does not run `npm run test:unit` or the
Playwright screenshot suite.** Nothing stops a PR with failing unit tests or a
broken UI from merging except this checklist being followed locally, by
whoever (human or Claude session) opens the PR. Treat every step below as
mandatory even though a green CI check does not prove it happened.

## Commands

| Task | Command |
|---|---|
| Type-check | `npm run typecheck` (or `npm run build`, which also bundles) |
| Unit tests | `npm run test:unit` (vitest) |
| Screenshot / visual regression tests | `npm run test:screenshots` (Playwright, builds the test harness first via the `pretest:screenshots` hook) |
| Update screenshot snapshots | `npm run test:screenshots:update` (also auto-copies the 4 canonical PNGs into `docs/` via `posttest:screenshots:update`) |

There is no separate E2E suite — the Playwright screenshot suite against
`test/harness/` (a mocked Obsidian environment, see `test/harness/obsidian-mock.ts`)
is this project's closest equivalent and doubles as visual verification.

## Coverage Requirements

- No enforced minimum coverage threshold.
- Every new or changed code path in `src/` should have a corresponding test
  in `test/unit/` — this repo's existing convention is thorough per-module
  unit tests (see `test/unit/BridgeManager.test.ts`, `WorktreeAutoFlip.test.ts`,
  etc.), including error-path and Notice-surfacing assertions, not just the
  happy path.
- Do not delete or skip an existing test to force a green suite.

## Visual Verification

This is an Obsidian desktop plugin (Electron), not a responsive web app —
there are no mobile/tablet breakpoints to check. Skip this step entirely if
no UI file was touched (`src/SettingsTab.ts`, `src/BridgesSidebarView.ts`,
`src/FileCommandBar.ts`, `src/WorktreeSwitchModal.ts`, `src/AddBridgeModal`,
`src/ConflictResolutionModal.ts`, `src/DirtyWarningModal.ts`, or `styles.css`).

When UI is touched:

- **Viewport:** fixed at 860×620, device scale factor 2, Chromium
  (`playwright.config.ts` — there is only one, this isn't a responsive
  surface).
- [ ] Run `npm run test:screenshots` — if any snapshot fails, either fix the
      regression or, if the new appearance is intentional, run
      `npm run test:screenshots:update` and review the diff before committing.
- [ ] Confirm the 4 canonical screenshots in `docs/` (`screenshot-settings.png`,
      `screenshot-empty.png`, `screenshot-add-bridge.png`, `screenshot-error.png`)
      still represent the current UI if the change touched Settings, the
      empty state, the Add Bridge modal, or an error state.
- [ ] No unexpected overflow, misaligned Setting rows, or broken button state
      in the modal(s)/sidebar/settings tab touched by the change.

## Docs Location

User-facing docs live in `docs/` (`getting-started.md`, `bridges.md`,
`troubleshooting.md`, `use-cases.md`, `development.md`, `windows.md`) and
`README.md`. Review and update any page related to the changed feature —
in particular:

- `docs/bridges.md` for anything touching bridge behavior (push/pull/switch
  worktree/auto-flip/dirty handling).
- `docs/troubleshooting.md` if the change fixes a failure mode a user could
  have hit (add a "why this happened" entry rather than just closing the PR).
- `docs/development.md` if the change affects the dev workflow, test
  commands, or worktree conventions.

## Issue Tracker

Not used in this repo (no Linear/Jira integration). No action needed.

## Project-Specific Gates

- **Worktree-first workflow is mandatory for this repo.** Never edit
  directly on the `main` checkout — create a worktree
  (`git worktree add .claude/worktrees/<branch> -b <branch>`), enter it via
  `EnterWorktree`, make the change there, then push the branch and open a PR.
  (Enforced by a PreToolUse/PostToolUse hook — see `Claude/coding-task-workflow.md`
  in the vault — but follow it by convention even if the hook is ever
  bypassed.)
- Changes to `src/BridgeManager.ts`, `src/WorktreeAutoFlip.ts`, or
  `src/VaultBridgesAPI.ts` (the git/worktree/dirty-state machinery) are
  higher-risk than average — prefer adding a regression test that reproduces
  the exact failure mode over a fix without one. Silent failures in this area
  (a flip that doesn't persist, a push that lands on the wrong branch) are
  hard for a user to notice until much later.
- `npm run version` (via `version-bump.mjs`) and publishing a GitHub release
  with built artifacts is a separate release step, not part of a normal
  feature PR — don't bump `manifest.json`/`versions.json` unless the PR is
  specifically a version bump.
